# Daedalus

Daedalus is a Chrome-extension-based remote control system for matching web pages — eval bridge, screenshots, CDP, cookies, network capture, hotfixes, declarativeNetRequest blocking.

Read `README.md` first — it is the reference for the command surface, install, and usage.

<architecture>
Single delivery mode: Chrome extension (MV3); the legacy Tampermonkey userscript is gone.

**Extension (`extension/`)**
- Token: auto-generated on first install, stored in `chrome.storage.local`.
- `content.js` (ISOLATED world): message relay between page and background. On load it asks the background to replay hotfixes (`replayHotfixes`); the background picks the eligible fixes from the extension-wide `daedalus-hotfixes` record and runs each through the eval routing below, so a page whose CSP forbids dynamic compilation is reached over CDP. Hotfix source is page-observable by design — it executes in the page — but is no longer posted into it.
- `page.js` (MAIN world): the last-resort page relay's `new Function` / `eval` and Blob-script paths, reached only after the background's source-free probe and CDP fallback cannot run submitted source. A hostile same-tab page can choose the relay's one-shot JavaScript value. Exposes the documented `window.GM` Tampermonkey-style subset (`xmlhttpRequest`, `openInTab`, storage methods, `addStyle`, etc.); cookie operations remain typed operator commands, with no page-facing `GM.cookie` surface.
- `background.js` (service worker): SSE stream, command dispatch, fetch relay, screenshots, CDP, cookies, tabs, downloads, notifications.
  - Eval routing: a constant MAIN-world `Function` probe carrying no submitted source runs first. `true` selects banner-free `page-main` injection; any other result selects the CDP CSP fallback, whose successful attachment shows Chrome's debugger banner. Once either channel dispatches submitted source, every outcome is terminal; only attach or shape failure before source runs reaches the page relay.
  - CDP `Runtime.evaluate` uses REPL mode, reads direct values by reference, bounds promise settlement at 10 seconds, and releases result and exception handles even when a kept session or capture holds the attachment.
  - Trust: a page you do not control can choose the returned value on any channel. On `page-main` its own `eval` and `Function` bindings can also read the submitted source; on `cdp` it can choose the value whenever that source uses page-controlled state or page promise machinery. The `world` field (`page-main`, `cdp`, `page:<hostname>`) records the channel, not whether to trust the value; the background adds the mandatory `page:` prefix, so relay hostnames cannot collide with the other two — a descriptive property, not a trust boundary.
  - The relay admits 1,000 live entries; a new one at capacity gets a terminal error without eviction, and a live entry expires with one terminal error after 300,000 ms.
- Tab tracking: `chrome.tabs` API, registered on create/update with a 30s `chrome.alarms` heartbeat.

**Server (`server.py`)**
- Restart the bridge process after editing `server.py`.
- `DAEDALUS_DIR` (command/result/upload root) and `DAEDALUS_PORT` are both required; the bridge refuses to start without either.
- Reverse proxy: the vhost fronting the bridge (update + reload when endpoints change).
- `server.py` keeps the process entry point, `ThreadingHTTPServer`, `Handler(RequestMixin)` with its `do_*` verbs and the request-path comparisons that dispatch them (`parsed.path == '/x'` where the query matters, `self.path == '/x'` on the body verbs), `GET /health` and `PUT /command`. Every other route body lives in a `daedalus_bridge` module:
  - `http_transport` — the `RequestMixin` a Handler derives from: request-target and query parsing, bearer/query/body credential resolution, the body-length refusal rules, the refusal drains, `answer` and `send_file`. The only bridge module that reads `config`, because it is transport rather than a route.
  - `json_body` — `json_nests_deeper_than` and `JSONObject`, body parsing rather than transport, so it binds no configuration of its own.
  - `route_answer` — `FileAnswer` and `BytesAnswer`, stdlib-only and re-exported by `http_transport`, so a route importing an answer type does not inherit that configuration requirement.
  - `tab_registry` — the registry dictionary and its lock, behind `GET /tabs`, `POST /register`, `POST /sync-tabs` and `POST /unregister`.
  - `stream_route` — `resolve_targets` and the `GET /stream` SSE loop.
  - `stream_service` — stream registration and replacement, the queue and legacy drains, and `POST /poll`; that one route body lives in a service module because it takes the same legacy claim the drain takes.
  - `upload_routes` — `POST`/`GET`/`DELETE /upload`, `GET /screenshot` by `id` and by `path`, and the single screenshot-format table all three consult.
  - `static_routes` — `GET /dashboard[/<asset>]` and the frame-refusing headers every dashboard response carries.
  - `result_routes` — `POST /result` and `GET /result`.
  - `segment_routes` — `POST /segment`, `GET /segment-status`, `GET /segment-job`; `segment_jobs` — the `POST /segment-job` mint.
  - State and helpers the routes call, unchanged by the split: `command_queue` (queue-file lifecycle), `result_store` (result slots and delivery files), `segment_store` (job records and usage accounting), `delivery_stripes` (delivery-lock striping), `path_safety` (component and containment checks), `atomic_file` (atomic replacement), `config` (startup paths and settings), `env_config` (the shared refused-body drain size, the bounded `env_int` / `env_positive_float` readers both front ends parse their settings with, and `debug_timing`, the shared reader that owns the `DAEDALUS_DEBUG_TIMING` name for the two modules that snapshot it and is true only for `1` — those read the environment when called), `log_safe` (rendering untrusted values), `parent_watch` (exit with the launcher), `mcp_bootstrap` (the optional MCP front end).
- Answer convention: a route function returns `(status, payload)` or a `FileAnswer`/`BytesAnswer`, never `None`, and never writes to the socket — the Handler writes it with `self.answer(...)`.
- Every route module and both stores bind no configuration of their own: a store takes its root directory and its limits as parameters, so it imports with no bridge configuration set, and a route's directory argument governs every file the request writes.
</architecture>

<endpoints>
Use these when writing server changes or constructing raw HTTP requests. Field names are exact.

Repeated authority carriers are rejected before any value is selected, including equal or blank repeats: `token` in a query or JSON body, a repeated `Authorization` header, a repeated `X-Daedalus-Segment-Sig` (400 `duplicate segment capability header`), and `job` / `sig` on segment-capability routes.

Authenticated `GET` routes resolve `Authorization: Bearer <token>` first and fall back to `?token=`; a header and a query token in one request must name the same one, or the answer is 400 `conflicting token`. `POST /segment` and `GET /segment-status` take their job capability from `X-Daedalus-Segment-Sig`, falling back to `sig` in the query, on the same rules. Every in-repo client sends the header form, so no reusable credential is written into a request target.

Body-reading verbs (`POST`, `PUT`, `DELETE`) settle credentials from `Authorization: Bearer <token>` before the body is read. A body `token` is still accepted, but only for a declared body within `DAEDALUS_MAX_UNAUTHENTICATED_BODY` (default `64 * 1024` bytes) — a larger body with no header is answered 401 unread, since a body token cannot be checked without reading the body. Two carriers are allowed only when they name the same token; differing ones answer 400 `conflicting token`. `POST /segment` is unaffected: it authorizes on the query string and the request headers, and never reaches this gate.

- `GET /stream?token=X&tab=Y` — SSE command stream. Extension uses `tab=extension` and picks up all tab-targeted commands. Liveness is policed by a keepalive comment every `DAEDALUS_STREAM_KEEPALIVE` seconds (default 15) — a dead peer raises on the next write — and by replacement when the same `(token, tab)` reconnects. `DAEDALUS_STREAM_MAX_AGE` (default 3600) is only a last-resort ceiling on a wedged connection, not a rollover timer. The response carries `Connection: close`, which is load-bearing: `keep-alive` makes `BaseHTTPRequestHandler` hold the socket open after the stream loop ends, so the client sees silence instead of EOF and its reconnect waits out a watchdog.
- `POST /poll` — consume the token's legacy broadcast command file `commands/<token>.json` (body: `{token}`), for a client that holds no SSE stream. It takes the same logical claim the SSE drain takes, so one command reaches one consumer: the answer is the command object, or `{}` when there is none or a draining stream holds the claim.
- `GET /tabs?token=X` — list active tabs, each with the `age` in seconds since its last registration. Nothing is pruned by age: an entry lives until it is unregistered or replaced by a sync.
- `POST /register` — refresh an existing tab entry (body: `token`, `tabId`, `url`, `title`; the first two are required). It does not create an entry; `POST /sync-tabs` replaces the token's registry and supplies new tabs. The answer is `{ok, updated}`: `updated` is false when the registry held no such tab, which is the signal to re-sync rather than keep refreshing an entry that is not there.
- `POST /result` — where the extension posts results. The server exposes a nonempty command `_did` as `deliveryId`, assigns a fresh `resultGeneration`, and writes the shared result slots while holding the result lock. For a delivery id, one per-target lock is acquired first and owns the delivery write, acceptance stamp, eviction, and cross-copy cleanup; the result lock is nested only after it. That lock is one of a fixed set of stripes keyed by a per-process secret, so which targets share a stripe is neither computable nor steerable offline and is visible as the wait a delivery write can incur; the bridge accepts that discovery, because a bounded stripe table costs less than an unbounded lock table keyed on caller-named targets. A nonempty delivery id is also retained at `results/deliveries/<target>/<deliveryId>.json`. A delivery id already stored is answered `{ok, duplicate: true}` with both slots and the dashboard stream left untouched, so a retried result never republishes over a newer one; the record of stored delivery ids is in-memory and bounded at 4096.
- `PUT /command` — submit command: `{token, tab, id, code}` for eval, or `{token, tab, id, type, ...}` for typed extension commands. Enqueues into a per-target directory queue (FIFO); back-to-back commands to the same tab queue instead of overwriting. Response includes the assigned `did` (delivery id); the delivered SSE frame carries it as `_did` so the extension can dedup a redelivered command. Commands unclaimed for `DAEDALUS_CMD_TTL` seconds (default 90) are dropped rather than delivered stale.
- `GET /result?token=X[&tab=Y]` — peek at the current shared result slot without deleting it. Add `&delivery=D` to select exactly delivery `D` from the per-target delivery directory; when `tab` is omitted, the bridge searches that token's target directories as well as its broadcast directory, and an absent delivery answers `{pending:true}`. `consume=1` applies the same consume semantics to either path: with `expected=<resultGeneration>`, deletion occurs only when that generation still occupies the selected result and a replacement is left in place with `{consumed:false}`; without `expected`, this remains a destructive compatibility read that returns the deleted body. Consuming either path normally removes a matching copy in the other path while preserving any newer slot generation. A compatibility consume that exhausts its bounded retry under continuous delivery-id replacement consumes the current slot under the result lock without mirrored cleanup; that delivery copy remains for later eviction.
- `GET /health` — bridge liveness: `{ok, uptime_s, active_streams, stream_tabs, registry:{tokens,tabs}, last_delivery_s_ago, cmd_ttl_s, stream_max_age_s, mcp}`. `active_streams` counts live streams, one per connection — a stream that named no tab is counted too, and appears in `stream_tabs` as `''`. `mcp` is the optional front end's startup state: `starting` until its listener binds, `up` from bind until the serve thread ends, `down` once it ends (under the bridge the caught crash's return is the only thing that ends it) or the front end's import failed. It carries no error detail — the verbatim bind error stays on stderr — because /health is unauthenticated. No token required (exposes no secrets). Use it to detect a silently-dead stream from the server side.
- `POST /upload` — store files: `{token, id, data (base64), format}` or `{token, id, data, filename}`.
- `GET /upload?token=X[&id=Y]` — list uploaded files. Optional `&limit=N&offset=M` (default limit 200 when either is set) returns `{items, total, limit, offset}` instead of a bare array. A page bounds the work as well as the answer: every stored file is counted, because `total` says how many pages there are, but only the page's own files are statted for size and mtime.
- `DELETE /upload` — remove: `{token, id, filename}` | `{token, id}` | `{token}`.
- `GET /screenshot?token=X[&id=Y]` — serve latest screenshot.
- `GET /screenshot?token=X&path=P` — serve exactly the file `P` names, where `P` is the `path` `POST /upload` returned and a screenshot result carries (`<token>/<id>/<file>`). `path` wins over `id`. Every component is checked like any other, the leading one must be the caller's own token (404 otherwise), and the suffix must be a screenshot type. Screenshot ids are reused, so an `id` fetch answers with whichever capture finished last; CLI and MCP clients download by `path`.
- `GET /dashboard[/<asset>]` — serve the web dashboard (HTML + ES modules) from `dashboard/` in the repo. A reverse proxy routes it to the bridge; paths containing `..` are rejected. Every dashboard response carries `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`, so the token-bearing control surface cannot be framed by another origin.
- `POST /segment-job` — mint (or re-fetch) an HLS job's segment capability: `{token, job}` → `{ok, sig}`. Idempotent for the owning token; 409 when the job name is owned by a different token; 500 when a record exists but cannot be read, which is never replaced by a fresh mint.
- `GET /segment-job?token=X&job=Y` — look the capability up **without minting**: `{ok, sig}` for a job this token owns, 404 when no record exists, 409 when another token owns it. This is what a status query uses; the POST creates a job it has not seen, so asking through it created the job being asked about.
- `POST /segment?job=X&seg=N&total=T` — raw binary HLS segment storage (`$DAEDALUS_DIR/segments/{job}/{seg:06d}.ts`); the job-scoped capability from `POST /segment-job` travels in `X-Daedalus-Segment-Sig` (or, still, `&sig=S`), never the bridge token. Everything the route authorizes on arrives before the body does, so the capability, the parameter shapes and the index bound are all settled first: a refused request is answered without buffering the segment it named.
- `GET /segment-status?job=X` — list received segments `{done[], count}`; capability in `X-Daedalus-Segment-Sig` or `&sig=S`.

`DAEDALUS_MAX_BODY_SIZE` (default `64 * 1024 * 1024` bytes) bounds every request body read by `POST`, `PUT`, and `DELETE`; a request with no `Content-Length` at all returns 411, an invalid or negative `Content-Length` returns 400, and a declared body over the limit returns 413. `DAEDALUS_REQUEST_TIMEOUT` (default 60 seconds) is the per-socket-operation deadline on the request line, headers and body alike; a declared body that stops arriving returns 408 and releases its worker instead of being waited on. `DAEDALUS_MAX_REQUEST_WORKERS` (default 256, range 1-4096) caps concurrently-served connections — past it a connection is closed without an answer rather than given a thread, so an SSE stream counts against it for as long as it is held. `DAEDALUS_MAX_JSON_DEPTH` (default 100, range 1-500) bounds how deeply a JSON request body may nest containers; the raw bytes are scanned before `json.loads` is called, so a body past the bound returns 400 `JSON body too deeply nested` on every interpreter rather than depending on whichever recursion limit the running Python happens to have.

`DAEDALUS_MAX_DELIVERY_RESULTS` (default `1024`) normally caps the unconsumed per-delivery result files retained for each target. Eviction goes by persisted acceptance stamps, not delivery-id spelling; ties, equal or unknown stamps, failed timestamp updates, and filesystem eviction failures all favor retention, so a target may sit above the cap until a later successful write trims it.

Filesystem-backed caller values share `_unsafe_component`: reject `..`, C0/C1 controls, surrogate code points, Windows-invalid path characters and device names, trailing dots/spaces, and UTF-8 encodings over 240 bytes. Tokens are also nonempty and reject dots and underscores. Accepted job names can still contain query delimiters such as `&` and `#`, so URL construction must encode them.

Every newly minted segment job records fixed values from `DAEDALUS_MAX_SEGMENT_INDEX` (default `99999`), `DAEDALUS_MAX_SEGMENTS_PER_JOB` (default `10000`), and `DAEDALUS_MAX_SEGMENT_JOB_SIZE` (default `4 * 1024 * 1024 * 1024` bytes). Existing jobs with valid quota fields continue to use their recorded values; the request-body limit separately caps each segment POST.

The dashboard subscribes to `/stream?tab=dashboard`. Events (not commands) are enqueued into `commands/{token}_dashboard/<ts>_<uuid>.json` by `_notify_dashboard` in server.py; the SSE loop drains that directory per tick. Emitted from: `/register` (`tab-updated`), `/sync-tabs` (`tabs-synced`), `/unregister` (`tab-unregistered`), `/result` (`result`). Dashboard frames carry `kind: 'event'`; broadcast eval frames that also reach the dashboard stream are ignored client-side.
</endpoints>

<directories>
- Commands: `$DAEDALUS_DIR/commands/` — directory queues drained FIFO by the SSE loop: `<token>_<tabId>/<seq>.json` (per-tab), `<token>/<seq>.json` (broadcast), `<token>_extension/<seq>.json` (typed extension commands), `<token>_dashboard/<ts>_<uuid>.json` (dashboard events). `<seq>` is `<ms>_<counter>`, lexically sortable. Legacy single-file drops (`<token>.json`, `<token>_<tabId>.json`) are supported only through sibling `.tmp` write plus same-directory atomic rename. Readers ignore `.tmp` names and leave malformed visible final files untouched so an in-progress older writer is never unlinked. Complete files older than `DAEDALUS_CMD_TTL` (default 90s) are TTL-dropped.
- Results: `$DAEDALUS_DIR/results/` — `<token>_<tabId>.json` + `<token>.json` (last-writer-wins compat), plus `deliveries/<token>_<tabId>/<deliveryId>.json` (or `deliveries/<token>/<deliveryId>.json` for a broadcast result) for independently consumable deliveries, capped and evicted as described under `DAEDALUS_MAX_DELIVERY_RESULTS`. The fixed `deliveries/` namespace keeps delivery directories structurally separate from slot files, so accepted dotted tab names cannot make one path both a slot and a directory. Results accepted through `POST /result` receive `resultGeneration`; those carrying `_did` also receive `deliveryId` for invocation matching.
- Uploads: `$DAEDALUS_DIR/uploads/<token>/<id>/` — screenshots + generic files.
- Segments: `$DAEDALUS_DIR/segments/<job>/` — HLS segment relay; `<job>.json` beside the directory records the owning token, the minted capability, the fixed quotas, and the running `stored_count` / `stored_bytes`. The write path enforces quotas from those totals and never counts the directory; a record without them is converted by one count on its next write, and a fresh mint seeds them by counting (which is also where a crashed write's `.ts.tmp` is swept). `DAEDALUS_DEBUG_TIMING=1` prints a per-phase `[SEGMENT-TIMING]` line per segment write and is inert otherwise.
- Dashboard assets: `dashboard/` in the repo (served by server.py at `/dashboard`).
</directories>

<mcp>
An MCP server runs in-process alongside `server.py` on `127.0.0.1:8086` (streamable-HTTP transport), fronted by the reverse proxy at `<your-bridge>/mcp`. `daedalus_mcp/server.py` composes the listener; `daedalus_mcp/auth.py` supplies its authentication middleware, `daedalus_mcp/request_guard.py` decides pre-body refusals, `daedalus_mcp/transport.py` owns bridge HTTP sessions, and the seven `daedalus_mcp/tools_*.py` modules define and register the tool groups.

Before dispatch it requires `Authorization: Bearer <bridge-token>` to exactly match the token resolved through the CLI's existing configuration path (`TOKEN`, otherwise `DAEDALUS_TOKEN`, including the optional `_settings` provider); no configured token fails closed with `401`. It rejects repeated `Authorization`, `Mcp-Session-Id`, `Host`, and `Origin` headers, and repeated `job` arguments for `segment_job` / `segment_status`, without selecting one value. Credentials are decided before the body is read, so an unauthenticated request is never materialized or parsed; a declared body over `DAEDALUS_MCP_MAX_BODY_SIZE` (default `64 * 1024 * 1024` bytes) is refused with 413 before reading, and an undeclared one is bounded after.

`DAEDALUS_MCP_PORT` (default 8086, range 0-65535) and `DAEDALUS_MCP_MAX_BODY_SIZE` are parsed with the same bounded reader the bridge uses, so an invalid value stops startup with a message naming the setting rather than an import-time traceback. Public-hostname allowlist via `DAEDALUS_MCP_ALLOWED_HOSTS` — DNS rebinding protection is enabled explicitly, so that list is the whole allowlist and the transport's own localhost default does not apply.

The bridge listener is bound before MCP starts, and its actual loopback URL is passed into the MCP HTTP client, including for `DAEDALUS_PORT=0`; `DAEDALUS_LOCAL_URL` remains the explicit standalone override. Remotely callable MCP tools accept inline JavaScript and CSS only: `put`, `inject_css`, `remove_css`, and `store_hotfix` have no server-local path argument. CLI file arguments are read by the CLI process and sent as inline content.

40 tools, registered by seven group modules:
- **Tabs**: `list_tabs`, `open_tab`, `open_tabs`, `focus_tab`, `close_tab`, `ext_navigate`, `ext_reload`
- **Eval / debug**: `exec`, `put`, `result`, `ping`, `navigate`, `reload`, `title`, `url`, `ext_self_reload`
- **Media**: `screenshot` (optional `include_image=true` to inline bytes), `segment_job`, `segment_status`, `uploads`, `delete_upload`
- **Cookies**: `get_cookies`, `set_cookie`, `remove_cookie`, `clear_cookies`
- **CSS / blocking**: `inject_css`, `remove_css`, `block_requests`, `unblock_requests`, `list_block_rules`
- **Hotfixes**: `store_hotfix`, `clear_hotfix`, `clear_hotfixes`, `list_hotfixes`, `set_permanent`
- **Network / CDP**: `net_capture`, `net_capture_stop`, `net_capture_get`, `cdp`, `fetch_timings`

`net_capture`'s `max_requests` is an integer from 1 to 20000 (`daedalus_mcp/tools_network.py`'s `NET_CAPTURE_MAX`, the same ceiling the CLI's `--max` and the extension both enforce); the buffer lives in the service worker and grows to hold headers and bodies, so the bound is a memory budget rather than a preference.

Manual verification helper: `TOKEN=<tok> python3 scripts/mcp_probe.py list|call <tool> [json-args]`.
</mcp>
