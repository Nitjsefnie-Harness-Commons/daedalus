Comprehensive repository audit guide

A full-repository audit is not a long code review. It is a bounded evidence exercise across source, live behavior, repository administration, external automation, release consumers, retained data, and project continuity. Use this guide to define the boundary before discovery, prove every claim against an exact snapshot, and make omissions visible instead of silently treating unexamined surfaces as clean.

What this guide prevents
Category blindness. A source-heavy audit can still miss repository settings, access grants, webhooks, contributor automation, mixed-version behavior, data retirement, and maintainer continuity. Completion is measured against the domain register below—not by the number of files read or issues filed.

Audit contract

Write this before inspection. A category not named here is not implicitly clean.

Required charter

  1. Objective: what decision the audit must support.
  2. Subject: repository, owner, default branch, products, deployed instances, and external services.
  3. Authority: read-only versus mutation, credentials available, and live-environment limits.
  4. Snapshots: starting source SHA, settings-capture timestamp, and final reconciliation SHA.
  5. Standards: repository policy, threat model, compatibility promises, service objectives, and legal obligations.
  6. Exclusions: every deliberately skipped surface plus the reason and residual risk.

Rules of evidence

  • Distinguish observed behavior, source inference, configuration state, and documentation claims.
  • Record exact commands, inputs, exit codes, timestamps, SHAs, API endpoints, and artifact identifiers.
  • Use fresh, paginated API reads for mutable control-plane state; never infer settings from workflow comments.
  • A passing test proves only its asserted behavior. Inspect assertion strength and failure sensitivity.
  • Absence claims name the search space and query. “Not found” without scope is not evidence.
  • Keep severity, exploitability, confidence, and implementation difficulty as separate fields.

Evidence ledger
Give every probe an ID. Record domain · claim · source · command · expected result · actual result · snapshot · confidence. A finding can cite several probes; a probe may also close a candidate as a non-finding.

4

Domain register

Set each domain to complete only when its evidence modes and exclusions are recorded. Progress and notes persist in this browser.

D01Scope, snapshots, and prior work
  • Pin source, settings, and execution snapshots.
  • Inventory prior audits, open and closed issues, accepted risks, incidents, and release notes.
  • Define duplicate rules and the final moving-head reconciliation procedure.
  • Name every excluded surface and who accepted the residual risk.
Done when
Another auditor can reproduce the subject and distinguish audited, excluded, and newly introduced surfaces.
D02Architecture and boundary inventory
  • Map extension, bridge, CLI, MCP, dashboard, reverse proxy, storage roots, GitHub, and external Actions.
  • Trace data, credentials, authority, and trust transitions between every pair.
  • Enumerate entry points, background workers, queues, scheduled tasks, and generated artifacts.
  • Compare documentation diagrams with actual imports, listeners, routes, and deployments.
Done when
Every externally reachable or privileged component has an owner, inputs, outputs, trust level, and failure boundary.
D03GitHub repository settings and feature surface
  • Record visibility, default branch, archived state, fork/template state, and enabled Issues, Projects, Wiki, Discussions, Pages, and sponsorship features.
  • Record merge methods, update-branch, auto-merge, delete-head, web sign-off, squash-message, and branch-name policies.
  • Inspect interaction limits, moderation, private vulnerability reporting, and contribution-admission settings.
  • Compare live settings with documented policy; do not infer settings from repository files.
Required evidence
Fresh repository, interaction-limit, Pages, and organization-setting responses with timestamps.
D04Administration, access grants, and integrations
  • Enumerate collaborators, outside collaborators, teams, role levels, pending invitations, and organization ownership.
  • Inventory deploy keys and whether each is writable; tie every key to a workflow or operator purpose.
  • Inventory webhooks, GitHub Apps, OAuth Apps, Pages deployments, external status/reporting services, and event subscriptions.
  • Check stale grants, single-person control, emergency access, credential rotation, and offboarding.
Do not collect
Secret values. Record names, authority, creation/update time, consumers, rotation owner, and deletion path.
D05CI, workflows, and repository automation
  • Inventory every workflow and job: triggers, filters, concurrency, permissions, environments, secrets, artifacts, caches, outputs, and required checks.
  • Threat-model pull_request_target, workflow_run, reusable workflows, fork input, issue/PR bodies, and comment commands.
  • Verify untrusted producers cannot choose privileged destinations, artifact identity, checkout SHA, cache contents, or executable text.
  • Exercise skip/failure/cancel/rerun paths and ensure aggregate gates cannot turn missing jobs green.
  • Diff workflow purposes, not only filenames: consolidation can hide growth, and a new job can create a new trust boundary.
Done when
Every write-capable token and cross-workflow handoff has an input-origin proof, destination binding, freshness rule, and visible failure path.
D06Dependencies and software supply chain
  • Inventory runtime, optional, test, build, workflow-action, browser, system, and hosted-service dependencies.
  • Check pinning, lock/constraint strategy, hashes, abandoned packages, install scripts, typosquatting, licenses, and update automation.
  • Run vulnerability and license scans with documented suppressions and freshness timestamps.
  • Inspect external Actions at their pinned revisions and record repository ownership/continuity.
  • Verify build isolation and that untrusted dependencies cannot alter release or coverage authority.
Evidence split
A scanner result is one input. Source ownership, install behavior, update path, and compensating controls remain separate evidence.
D07Build, release, provenance, and consumer verification
  • Trace tag or dispatch through tests, build, signing/attestation, checksum, upload, release publication, and post-release version movement.
  • Prove the artifact derives from the intended immutable SHA and contains only intended files.
  • Install wheel and source distribution outside the checkout; compare metadata and runtime behavior.
  • Verify a consumer can validate checksums and attestations from published instructions.
  • Review rollback, yanking, compromised-release response, retention, and channel policy.
Failure probes
Stale tag, partial upload, rerun, missing required job, wrong artifact name, duplicate release, and post-release patch.
D08Authentication, authorization, and exposed capability
  • Inventory credentials, minting, storage, transport, comparison, redaction, rotation, revocation, and scope.
  • Test missing, empty, duplicate, malformed, oversized, replayed, and cross-context credentials before body materialization.
  • Map browser/page/extension/bridge/MCP/operator authority; distinguish authentication from result integrity.
  • Review host/origin checks, DNS rebinding, framing, CORS, TLS termination, proxy headers, and loopback assumptions.
  • Confirm page-facing shims cannot reach reserved credential storage or operator-only capabilities.
Core question
For every action: who can request it, who can influence its parameters, where it executes, and what data it can return or mutate?
D09Data lifecycle, privacy, and decommissioning
  • Inventory commands, results, deliveries, uploads, screenshots, network captures, segments, logs, credentials, browser storage, dashboard storage, and hotfix code.
  • For each store, record owner, sensitivity, location, naming, quota, TTL, eviction, deletion, backup, restore, and migration behavior.
  • Test crash leftovers, malformed records, failed deletion, quota exhaustion, clock changes, and partial migration.
  • Define credential rotation, uninstall, repository removal, and whole-product secure decommissioning.
  • Check whether diagnostic bundles or logs can expose tokens, browsing data, page results, or user-authored code.
Category trap
Testing one storage API does not close the end-to-end retention and retirement lifecycle across components.
D10Concurrency, ordering, retries, and data integrity
  • Map ownership and ordering for queues, result slots, delivery records, tabs, streams, segment jobs, hotfixes, captures, and shutdown.
  • Probe duplicate, simultaneous, reordered, delayed, canceled, retried, and partially persisted operations.
  • Verify acknowledgements correspond to durable state and do not precede the effect they promise.
  • Check lock ordering, bounded lock tables, starvation, fairness, atomic replace, cross-process ownership, and cleanup races.
  • Prove idempotency keys and generations do not overwrite newer state or duplicate visible side effects.
Minimum dynamic set
Two writers, two readers, retry after ambiguous completion, crash between write phases, and shutdown during an in-flight operation.
D11Upgrade, rollback, and compatibility
  • Define supported Chrome, Python, operating-system, MCP protocol/client, proxy, and packaging combinations.
  • Test adjacent-release matrices across extension, bridge, CLI, MCP client, dashboard, stored hotfixes, and persisted records.
  • Exercise forward migration, interrupted migration, repeat migration, downgrade, rollback, and mixed-version recovery.
  • Review wire-format changes, defaults, deprecation windows, semantic-versioning policy, and unknown-field behavior.
  • Separate within-tree version equality from real cross-release compatibility.
Done when
Every independently updated component has a declared compatibility window, tested transitions, and a recovery path.
D12Reliability, recovery, and resource ownership
  • Trace startup, readiness, degraded modes, reconnect, parent death, duplicate processes, graceful shutdown, forced termination, and restart.
  • Inventory threads, subprocesses, sockets, CDP attachments, captures, timers, temporary files, and open handles.
  • Bound input reads, worker counts, queues, response sizes, retries, deadlines, and cleanup work.
  • Test disk full, permissions failure, corrupt state, port conflict, missing optional dependencies, browser disappearance, and proxy failure.
  • Verify backup/restore or explicitly document why ephemeral reconstruction is sufficient.
Recovery proof
Show the system returning to a known state after each injected failure; “logged an error” is not recovery.
D13Observability, diagnostics, and supportability
  • Define health semantics for bridge, MCP, streams, browser attachment, queues, storage, and external services.
  • Verify errors identify the failed phase and actionable next step without leaking secrets or attacker-controlled terminal content.
  • Check log levels, correlation IDs, clocks, safe rendering, diagnostic flags, and visibility of dropped or retried work.
  • Confirm documentation tells operators how to distinguish starting, healthy, degraded, disconnected, and irrecoverable states.
  • Keep diagnostic instrumentation real, inert when disabled, and reusable for the next regression.
Support test
Give evidence to a person who did not run the probe; they should locate the failing boundary without reconstructing the code path.
D14Performance, capacity, and denial-of-service resistance
  • Define representative operations, baselines, budgets, variance, warmup, machine profile, and comparison statistics.
  • Measure latency, throughput, memory, disk, CPU, file count, network bytes, runner time, and browser impact.
  • Scale retained commands/results/segments/tabs/hotfixes and vary payload size, concurrency, and rejection timing.
  • Look for repeated scans, quadratic behavior, amplification, buffering copies, base64 expansion, and cleanup cliffs.
  • Validate performance gates report real regressions and cannot hide them through aggregation or incomplete rounds.
Measurement rule
Keep raw samples and the exact benchmark command. A ratio without its populations, exclusions, and noise floor is not evidence.
D15Tests, coverage, and assertion strength
  • Map tests to components, threats, public contracts, failure modes, platforms, and workflows—not only files.
  • Measure Python and JavaScript separately; combine subprocess data correctly and identify excluded shipped code.
  • Inspect weak assertions, tautologies, overmocking, arbitrary sleeps, nondeterminism, skips, order dependence, and cleanup leaks.
  • Mutation-test high-risk guards and gates: unauthorized, oversized, stale, wrong-SHA, partial, and concurrent cases.
  • Verify local commands match CI, fresh-install tests leave the checkout, and required jobs actually execute on relevant changes.
Coverage rule
Coverage locates unobserved code. It does not prove assertions, behavior, or boundary completeness.
D16Documentation, UX, accessibility, and internationalization
  • Run every quickstart from a clean environment; check command help, examples, error recovery, security warnings, and release verification.
  • Compare public routes, flags, environment variables, defaults, storage behavior, and limitations with code.
  • Audit keyboard access, focus order, labels, names, live regions, contrast, reduced motion, zoom, and error announcement.
  • Test empty/loading/error/partial/stale states in extension options and dashboard.
  • Assess locale-sensitive parsing, time zones, Unicode, text expansion, and whether internationalization is intentionally out of scope.
Consumer proof
A new operator can install, verify, recover from one failure, and remove the product using published instructions.
D17Maintainability and architectural fitness
  • Measure file/module growth, responsibility count, dependency direction, duplicated contracts, generated drift, and dead paths.
  • Review public interfaces, naming, error taxonomy, configuration ownership, and whether boundaries can be tested independently.
  • Inspect TODO/FIXME markers, ignored checks, suppressions, accepted-speed changes, coverage exclusions, and policy exceptions.
  • Use automated size or complexity ratchets where growth is the risk; prove the ratchet covers every shipped source family.
  • Check contributor changes can be reviewed without holding an entire monolith or implicit protocol in memory.
Finding threshold
File size alone is a signal. Tie a finding to mixed responsibilities, unsafe change coupling, review limits, or missing enforceable boundaries.
D18Governance, ownership, and maintainer continuity
  • Identify who can administer, merge, release, rotate secrets, respond to incidents, moderate, and reverse a bad change.
  • Compare CODEOWNERS, teams, collaborators, protected resources, package ownership, and actual contribution concentration.
  • Review succession, emergency access, maintainer unavailability, disputed decisions, conduct-report escalation, and release-key recovery.
  • Check support and security-contact promises remain valid when the primary maintainer is the subject or unavailable.
  • Document intentional single-maintainer risk explicitly rather than inferring resilience from public contributors.
Do not overclaim
Public APIs cannot prove the absence of private succession arrangements or organization-level emergency owners.
D19Legal, privacy, licensing, and responsible use
  • Verify repository and distributed artifacts carry the intended license, notices, attribution, and third-party obligations.
  • Classify personal or sensitive data reachable through cookies, screenshots, captures, page evaluation, uploads, logs, and browser storage.
  • Review consent, purpose limitation, retention, deletion, export, incident notification, and operator responsibilities.
  • Check examples, proof-of-concepts, and issue-report instructions prohibit attacking third-party systems.
  • Record jurisdiction- or deployment-specific obligations as explicit boundaries rather than issuing unsupported legal conclusions.
Evidence standard
State observable collection and control behavior. Label legal interpretation as specialist-dependent.
D20Deployment, operations, and external services
  • Inventory supported local and remote deployment shapes, reverse proxies, TLS, DNS, firewalls, ports, service managers, storage permissions, and update ownership.
  • Test proxy headers, streaming timeouts, upload limits, path routing, host allowlists, certificate renewal, and default-vhost behavior.
  • Review backups, restore drills, monitoring, alert routing, incident response, maintenance windows, and dependency outages.
  • Trace external service failure and revocation: GitHub, package indexes, browsers, Actions, attestations, code scanning, and webhooks.
  • Separate repository guarantees from operator-supplied deployment policy.
Done when
Every supported deployment has an install, health, update, backup, recovery, and decommission owner—even if the answer is “operator supplied.”

Control-plane failure mode
A denied endpoint is not an empty inventory. Record the HTTP status, required permission, and resulting blind spot. Never replace a settings check with a guess from YAML, documentation, or the repository’s public appearance. A 404 from legacy branch protection is also not proof that a branch is unrestricted: repository rulesets may still apply, so enumerate each ruleset, inspect its target and conditions, and query effective rules for each target branch.

Workflow threat model

Model each workflow as an authority pipeline: event → attacker-controlled fields → runner → credentials → side effects.

BoundaryQuestions that must be answered
TriggerWho can cause it? Which event types, branches, paths, actors, forks, schedules, or manual inputs qualify?
SourceWhich SHA is checked out or read? Base, head, merge, tag, default branch, artifact producer, or API response?
ExpressionCan titles, bodies, comments, filenames, matrix values, outputs, or JSON reach shell, paths, environment, or logs?
AuthorityWhat token permissions, secrets, OIDC claims, environments, deploy keys, bypass actors, or external Apps exist?
State transferHow are artifacts, caches, outputs, comments, checks, releases, or reusable-workflow results authenticated and bound?
ConcurrencyWhat is canceled, queued, retried, or made stale? Can an older run overwrite a newer result?
VerdictWhat counts as required success? Can skipped, missing, canceled, or renamed jobs satisfy the aggregate?

Finding standard

A candidate becomes a finding only after reproduction, duplicate discovery, and current-head validation.

Admission criteria

  • Concrete observed behavior or configuration state.
  • Expected behavior anchored to a contract, invariant, or stated risk.
  • Minimal reproduction with exact snapshot and command.
  • Demonstrated impact and affected boundary.
  • Fresh duplicate search across open and closed issues and pull requests.
  • Revalidated against the current default branch immediately before filing.

Reject or defer when

  • The claim is stylistic without a behavior or maintenance consequence.
  • The candidate restates an accepted design without contradictory behavior.
  • Evidence depends on an obsolete SHA and no current regression exists.
  • The only claim is that a historical audit missed a category, but evidence shows that category was covered. Still evaluate any distinct mechanism defect against the admission criteria.
  • The auditor cannot access the needed setting or environment; record a limitation instead.
  • The remediation is speculative and no invariant defines success.

Copyable finding template

Title: <observable failure or unsafe state> Observed behavior <What happened, without diagnosis or proposed fix.> Expected behavior <The contract, invariant, policy, or safety property.> Reproduction 1. Snapshot: <40-character SHA / settings timestamp / run ID> 2. Preconditions: <runtime, permissions, environment> 3. Command or actions: <exact and minimal> 4. Actual result: <exit code, response, state transition> Evidence - Probe IDs: <E-...> - Files/settings: <file:line or API endpoint/resource ID> - Artifacts: <path or run artifact> Impact <Who or what is affected; severity and confidence separately.> Suggested remediation <Concrete boundary or invariant to enforce; alternatives if material.> Verification <Test/probe that fails before the fix and passes afterward.> Discovered during <Audit name, domain, starting SHA, reconciliation SHA.>

Execution and fan-out

Parallelize independent domains, not overlapping writes or one causal chain.

Good fan-out

  • GitHub control plane and access inventory.
  • Workflows, CI, release, and supply-chain authority.
  • Code security, storage, concurrency, and reliability.
  • Tests, coverage, performance, documentation, accessibility.
  • Compatibility, operations, governance, privacy, and legal boundaries.

Return contract for each stream

  • Audited and excluded surfaces.
  • Exact snapshots and evidence commands.
  • Verified candidates, rejected candidates, and limitations.
  • Category gaps discovered outside the brief.
  • No issue filing until the lead deduplicates and revalidates.
Synthesis rule
Streams are lenses, not totals. The lead owns overlap removal, cross-domain findings, settings/source reconciliation, severity calibration, and the proof that every domain reached a terminal state.

Moving-head reconciliation

An audit of a moving repository needs both a starting snapshot and a final delta pass.

  1. Fetch the latest default branch without altering the audit checkout.
  2. Record the final 40-character SHA and compare it with the starting SHA.
  3. Classify changed files, workflows, settings, releases, issues, and external integration revisions by audit domain.
  4. Re-run affected probes and every candidate reproduction on the final snapshot.
  5. Refresh issue and pull-request duplicates; state changes do not erase mandatory inspection.
  6. For each old finding, record fixed, still open, regressed, accepted, superseded, or unverifiable.
  7. Do not count post-audit additions as historical misses. Label them new surfaces requiring coverage.
  8. Publish the starting SHA, final SHA, settings-capture time, and unresolved limitations together.

Exit criteria

The audit is complete only when all statements below are evidenced.

  • Every domain is complete or explicitly not applicable with a reason.
  • Every source, settings, and execution claim names its snapshot and evidence.
  • Every mutable list was fetched fresh and paginated; denied endpoints are limitations, not empty results.
  • Every candidate was reproduced, deduplicated, and revalidated on the final head—or rejected with a reason.
  • Every prior finding has a live disposition.
  • Post-start changes and post-audit additions were classified by domain.
  • Severity, confidence, exploitability, and difficulty were not collapsed into one label.
  • Tests and CI evidence name the exact SHA and include nonzero jobs from the intended workflow.
  • Clean domains and deliberate exclusions are visible alongside findings.
  • The report contains enough evidence for an independent auditor to challenge its conclusions.
